Module 1.1 Blog Post: Systems Thinking in Microsoft Security: Building a Shared Understanding

Seeing the Investigation as a System

When I think about systems thinking, I think about understanding how the parts of a system affect one another and contribute to a common purpose. Knowing what each part does is necessary, but it does not explain the whole system. I also need to understand the connections, the information moving between those parts, and the people making decisions from that information. In cybersecurity, this is significant because an investigation can involve several tools and several analysts, all looking at different pieces of the same situation.

The Microsoft security environment is a useful example. My focus is the connected environment around Microsoft Defender XDR, including identity, devices, email, cloud applications, and security monitoring. The purpose is to help people understand and respond to threats. However, the presence of capable tools does not automatically produce a clear or consistent investigation. Analysts can reach different conclusions from the same evidence. They may repeat work on the same sources and identities, while their individual strengths are not applied where they would contribute most.

Holt (2023) explains that systems engineering must address complexity, communication, and understanding. He also distinguishes complexity inherent in a system from complexity introduced through inefficient people, processes, and tools. I see repeated investigation work and unclear handoffs as examples of the second category. Some technical complexity is unavoidable in a large security environment. Repeating the same research because findings were not shared is a problem we can improve.

For me, systems thinking begins by asking what the investigation is supposed to accomplish and how the entire process supports that goal. An alert is an input to that process. A useful outcome is an evidence-based decision about what happened, what remains uncertain, and what action is justified. That outcome depends on how the components work together.

Understanding the Microsoft Environment

Microsoft describes Defender XDR as connecting protection across endpoints, email and collaboration, identities, and cloud applications. Defender for Endpoint addresses devices, Defender for Office 365 addresses email and collaboration threats, and Defender for Cloud Apps addresses cloud applications. Defender for Identity and Microsoft Entra ID Protection contribute identity protection. The cross-product capabilities bring related alerts, suspicious events, and affected assets together into incidents (Microsoft, 2026).

These relationships matter more to my example than memorizing product names. Exchange Online provides an email workload, while Defender for Office 365 provides security capabilities around email and collaboration. Entra ID provides the identity environment in which users access resources. Sentinel belongs in the broader security operations environment as an integrated monitoring service. I would not describe every connected service as a component owned by Defender XDR. Defining the boundary clearly helps explain which systems provide activity, which protect resources, and which help analysts investigate.

For this discussion, I would place the investigation workflow inside the system I am examining. That includes the security tools, the evidence they make available, the analysts, and their coordination. I would also identify the dependencies outside that boundary, such as business applications and approved software distribution services. The scope needs to be broad enough to explain the investigation without trying to represent every service in the organization.

A Linear Investigation

A straightforward linear investigation might begin with an alert about an unusual file download. The analyst identifies the file, checks its hash against threat intelligence, scans it for malware, and closes the alert if the results appear clean. Each step follows the previous step, and the investigation ends with a conclusion about that file.

That approach can be useful for routine triage. I would not suggest abandoning checklists or repeatable steps. The limitation appears when the investigation treats the file as an isolated event and assumes that a clean result answers the larger question. A file can be legitimate while the account downloading it is compromised. A clean scan also does not explain why a particular process contacted a domain or whether that activity was expected.

In a systems-thinking approach, I would still perform those checks, but I would also examine related activity. Did the download occur near a suspicious sign-in? Which process was responsible? What domain did it contact? Do the account and device connections support treating these events as one incident? The difference is the scope of the reasoning. Following an ordered process is compatible with systems thinking when that process examines the relationships needed to understand the situation.

A Shared Incident Timeline

The hypothetical investigation I would use contains four events: a suspicious sign-in, unusual domain communication, an unusual process, and an unusual file download. I would bring those events into a shared timeline before assuming they tell one story. Their actual order would come from the evidence. Putting events next to one another does not prove that one caused another.

The domain would be my first connection to investigate. I would examine its reputation, whether it is new to the environment, and what the process was doing with it. I would then ask whether the file download came from that domain and whether the process ran on a device associated with the suspicious sign-in. Each relationship needs support. Similar timing alone would leave too much room for assumptions.

There are several possible legitimate explanations. The domain might be organizationally sanctioned and have a long history of healthy activity. The process might be a benign updater downloading an expected file. Those findings would change how I interpret the communication and download. They would not automatically explain the suspicious sign-in, which could still require separate investigation.

This is why I prefer a shared timeline as the foundation for the team. Without it, one analyst might focus on the sign-in and conclude that an account is compromised. Another might recognize the updater and conclude that the activity is normal. Both could have useful information, but neither conclusion is complete until the team compares the evidence and identifies which relationships are confirmed.

A common timeline would make those differences easier to resolve. It would show what was observed, where the information came from, and what has already been checked. Analysts could add findings instead of starting the same investigation again. They could also identify questions that require another person's expertise. The goal would be to make disagreement productive by giving everyone the same foundation for evaluating it.

Using Models to Design the Investigation

Model-based systems engineering offers a way to design that foundation before an incident occurs. Holt (2023) describes a model as an abstraction of a system, with consistent views that serve different stakeholders. He also separates structural information from behavior. Applied to my example, one view could describe the tools and connections, while another could describe how evidence moves through the investigation.

Singam and Carter (n.d.) explain that MBSE uses formalized system representations to support engineering throughout the life cycle. Effective models describe requirements, structure, behavior, and component connections. They also explain why consistent information and maintained models are significant for communication and identifying problems. That gives me a way to connect the investigation example to the design of a complex digital environment, rather than treating the timeline itself as a complete MBSE implementation.

I would start with a structural view showing the relevant identity, endpoint, email, cloud application, and monitoring systems. The connections would identify the information each provides and where that information is used. A behavioral view would show how an event becomes available to investigators, how related evidence is checked, and how a decision moves toward response. Both views would describe the same environment and use consistent terms for accounts, devices, processes, domains, and files.

The shared timeline would be an operational view of a particular investigation. The engineering model would describe the capability required to produce and use that view reliably. For example, I would propose that every timeline entry identify its source, event time, associated entities, and verification status. I would also distinguish an observed event from an analyst's interpretation. Those are design requirements I would choose for this example, rather than claims about fields every Microsoft product automatically supplies.

The model would help the team ask what happens when a dependency fails. What if identity evidence arrives late? What if two tools identify the same account differently? What if a device does not provide the process information needed to connect a download to domain communication? Modeling those situations would expose gaps that could otherwise remain hidden until an investigation needed the missing evidence.

People and Decisions Still Matter

A shared model would also help clarify responsibilities. An analyst with strong endpoint experience could investigate the process and file activity. Someone with identity expertise could examine the sign-in. Another person could check the domain's business purpose. Their findings would contribute to a common investigation instead of becoming separate conclusions that compete without a shared context.

I would want the workflow to make completed work visible and allow analysts to challenge interpretations. A common foundation should support independent judgment. It should not pressure everyone to agree with the first conclusion entered into the incident. If evidence supports two explanations, the team should record what would distinguish them and investigate that question.

Response decisions also have effects beyond the alert. Blocking a domain could interrupt an approved updating service. Disabling an account could prevent legitimate work. Leaving suspicious activity unaddressed could allow an attacker to continue. I would use the model to examine those dependencies and choose a response supported by the evidence, with a clear understanding of the likely consequences.

The model would require maintenance as tools, applications, and workflows change. I would evaluate its usefulness by looking at repeated work, missing evidence, handoff clarity, and how well analysts can explain their decisions. I would treat improvement as something to measure, rather than assume that a shared dashboard guarantees it.

What Systems Thinking Changes

The main value of systems thinking in this example is a better foundation for understanding an incident. The tools provide different perspectives, and the analysts bring different experience. A shared timeline helps connect those perspectives to evidence, while a broader engineering model helps design the relationships and workflows that make the timeline useful.

I see MBSE as a practical way to make the security environment easier to explain, examine, and improve. It gives the team a way to identify dependencies and test possible situations before relying on them during an incident. For me, the strongest investigation is one in which people can show how they reached a conclusion, what connects the evidence, and what they still need to verify.

Module 1.2 Blog Post: Security Has to Work for the People Using It

A security policy can look right on paper and still stop people from doing their jobs. That is why systems life cycles are relevant. In a Microsoft security environment, enabling a control is only part of the work. The team also has to understand how people will use it, test whether it works in their environment, support it after deployment, and eventually replace it without leaving problems behind. A completed implementation plan means very little if legitimate users can't access the systems they need.

One example that stands out is a Conditional Access policy requiring phishing-resistant multifactor authentication (MFA). Broken or partial implementations can completely block users from the Microsoft services they depend on. The security goal makes sense, but the implementation has to account for actual users and workflows. This is why I favor testing and refining a system as the team learns what works. Plans establish a direction, but using the system shows whether it meets the need.

Understanding the Whole Life Cycle

I understand the systems development life cycle as the stages through which a system moves as its needs are identified, it is developed and produced, it enters use, it receives support and it is eventually retired. Holt (2023) describes conception, development, production, utilization, support and retirement as system life cycle stages. These stages make the scope larger than the initial implementation. They include the work needed to keep a system useful and to end its use responsibly.

Holt (2023) also distinguishes the life cycle from the life cycle model. The life cycle identifies the stages, while the model describes how those stages are executed. I find that distinction useful because identifying the necessary work does not automatically tell a team how to organize it. Two security projects might both need requirements, testing, deployment, support and retirement planning, yet need different approaches to moving through that work.

For a Microsoft security system, I would start with the need for protection and reliable access. Development would include choosing the approach and understanding its dependencies. Production would involve implementing and checking the solution. Utilization and support would include people using the system and the team responding to problems. Retirement would require a controlled transition and cleanup. Thinking through these stages makes it harder to treat deployment as the point where responsibility ends.

Linear Development: Structure With a Purpose

The linear life cycle model moves through stages in a defined sequence. Work in one stage is completed before the next begins, with delivery typically occurring at the end. Holt (2023) explains that this approach suits projects the team understands well, with clearly specified needs that are unlikely to change. Its advantages include simplicity, clear gates between stages and an understandable sequence of work.

I see value in that structure for a tightly controlled security change requiring formal approvals and documentation. The team needs to explain what is changing, establish responsibilities and provide a record of the decision. A defined sequence can make it clear when a proposal is ready for approval and when implementation can begin. It also gives reviewers something concrete to evaluate rather than asking them to approve an evolving idea without clear boundaries.

My concern is that following the plan can become more important than whether the system works for users. A team could complete its documented steps and consider a change successful while employees still can't access necessary applications. That would be a failure of the outcome even if the process had been followed correctly. Formal approval should establish accountability, but it should also depend on evidence that the change meets the needs it was supposed to address.

The MFA example shows how this can happen. A plan might call for configuring a policy, receiving approval and enforcing it on a scheduled date. If testing doesn't represent actual sign-in situations, that sequence could overlook a readiness problem. The drawback is the limited opportunity to learn and adjust before a broad release. I would use a linear approach where the requirements and controls justify it, while making successful user access part of the acceptance criteria.

Iterative Development: Learning From Actual Use

An iterative model makes multiple passes through the stages, producing working versions that are refined over time. Holt (2023) describes each iteration as a smaller life cycle that results in a workable version of the system. This gives the team opportunities to learn, improve the solution and respond to problems before treating the design as final.

This is the approach that matches how I think about improving a security system. Real users and workflows reveal problems that planning misses. A configuration can appear reasonable in a review and still behave differently when people use different devices or move between applications. Testing should help the team discover those differences and use them to improve the implementation.

With phishing-resistant MFA, I would combine a representative pilot with readiness checks. The test group should cover different devices, roles and sign-in situations. Before enforcement expands, users should have working authentication methods that satisfy the policy and a recovery path the support team understands. Microsoft (n.d.) recommends testing with representative pilot users, gathering feedback and using report-only Conditional Access results to identify sign-ins that would be blocked. That guidance supports checking readiness through evidence rather than assuming configuration equals successful deployment.

I would apply an iterative model by reviewing the pilot results, identifying why users couldn't sign in, making focused changes and testing again. The improvement might involve the configuration, enrollment process, instructions or support procedures. The next version should address what the previous version revealed. Repeating a test without acting on its findings would take time without improving the system.

The biggest drawback for me is time. Testing and rework take time away from other priorities, and security teams still have other responsibilities to meet. Iteration needs a clear purpose so it doesn't become an open-ended search for a perfect configuration. I would define what each test is intended to establish and what evidence would justify moving forward. That creates room for learning while keeping the work tied to a decision.

Incremental Development: Delivering Useful Capabilities

Incremental development delivers the system in usable portions. Holt (2023) explains that the concept stage addresses the overall needs, while development and production deliver subsets of those needs across releases. The advantage is that some functionality can be available before the entire system is finished. The limitation is that the system must be divisible into useful parts for this approach to work.

For Microsoft security, I would think about increments as complete capabilities. A first increment could establish a functioning authentication capability for administrator accounts. Later increments could deliver additional protection for other access needs or introduce another security capability. Each increment should have a defined purpose and enough supporting work to operate reliably. Enabling part of a capability while leaving its recovery or support arrangements unfinished would be a failure.

The distinction between incremental and iterative development matters. An increment adds a portion of the overall solution. An iteration improves a version based on what the team learns. A team could deliver an authentication capability as one increment and use several iterations to refine it. Incremental development determines which useful capability to deliver next, while iterative development helps the team improve the current solution.

My biggest concern with incremental development is that later improvements can keep getting postponed. The first capability receives attention because it is urgent, while the remaining work competes with new requests. The organization may continue operating with a partially completed plan long after that was supposed to be temporary. To address that, I would give later increments clear ownership and revisit their priority openly. Early delivery is valuable, but it should not make unfinished needs disappear from view.

Keeping the System Useful After Deployment

After deployment, my priority is whether users can work reliably and whether support teams can maintain the system. This is where life cycle thinking affects sustainability. A security system needs ongoing attention to remain useful, and the effort required to operate it matters. If every routine access problem requires extensive troubleshooting, the implementation creates a continuing burden even if its initial deployment was considered successful.

I would include support readiness in the design from the beginning. The team should understand the intended behavior, know how to investigate access failures and have clear responsibilities for resolving them. User instructions also need to match the actual experience. These are practical parts of the system because they affect whether people can use it consistently and whether the organization can keep supporting it with the resources available.

Ross et al. (2022) describe systems security engineering principles and activities as applicable regardless of a system's life cycle stage. That supports my view that security work continues throughout the system's existence. The implementation creates an initial result, but operation provides new evidence about how that result holds up. I would use that evidence to decide when a control needs refinement, when another capability is needed or when replacement becomes the more practical option.

Evolution should have a reason. I would want a proposed change to address a defined need, such as a recurring access problem or a support process that no longer works well. Otherwise, continual changes can consume the same limited time that makes iteration difficult. A sustainable approach gives the team a way to improve the system while keeping its operation understandable and manageable.

Retirement Is Part of the Design

Replacing a security system should preserve users' ability to work and include verified cleanup. Those priorities belong together. Moving to a new control without understanding the old dependencies could interrupt access, while leaving old policies or permissions behind could create confusion after the transition. I would want a plan that identifies what must remain available during the change and what should be removed once the replacement is working.

For the MFA example, that means considering how existing access policies and authentication arrangements relate to the replacement. I would verify the new sign-in path before removing dependencies that users still need, then check that the old configuration has been retired as intended. Holt's (2023) retirement stage reinforces why I would plan for the end of a system's use as carefully as its introduction.

The lesson I take from these models is that the approach should serve the system and its users. Linear development offers structure for controlled changes. Iterative development supports learning from actual use. Incremental development delivers useful capabilities while the broader solution develops. I favor iteration because user experience reveals gaps that a plan can miss, but I would combine it with clear approvals and deliberate capability planning. From conception through retirement, I would judge success by whether the system provides protection, allows people to work and remains practical to support.

Module 2.1 Blog Post: Security Tools Have to Make Sense to the People Using Them

A security tool can collect the right information and still make an investigation harder than it needs to be. If an analyst can't tell what's important, find the evidence behind an alert, or understand what an action will affect, the interface becomes another problem to solve. I think designing for people starts with recognizing that the person using a system has a job to do. Learning the interface shouldn't take attention away from that job.

Microsoft security tools are a useful environment for thinking through this. For this example, I'm considering an analyst investigating a possible account compromise using Microsoft Defender XDR and Sentinel. The design examples are changes I'd consider and test, rather than claims about a specific version of either product. The analyst needs to understand what happened, decide what evidence supports that conclusion, and determine whether a response is justified. Those decisions depend on how information is presented as well as what information is available.

Start With the Person and the Task

Human-centered design means building an understanding of people into the decisions that shape a system. That includes their goals, working conditions, experience and limitations. Asking whether a page looks organized is useful, but I'd also want to know whether someone can use it to complete an actual investigation. A design that makes sense to its developer might still leave an analyst unsure where to go next.

The assigned explanation of ISO 9241-210 makes direct user involvement central to the process. Franz and Kauer-Franz (2024) explain that desk research alone isn't enough. Designers need to understand users, their tasks and their environment, then bring user feedback into the development of the solution. I see that as a practical safeguard against building an interface around assumptions that nobody has checked.

For the investigation example, I'd begin by observing how analysts move from an alert to the supporting evidence. I'd want to understand what they compare, where they lose context and what they need before choosing a response. I'd also include different levels of experience. Someone familiar with the environment may fill in gaps automatically, while a newer analyst may need those relationships made explicit. Both perspectives can reveal something the design team would otherwise miss.

ISO and IDEO: Structure and Room to Learn

The ISO approach described in the course reading provides a clear structure: plan the process, understand the context of use, specify user requirements, produce design solutions and evaluate them. The diagram ends when the design meets user requirements, with iteration where needed (Franz & Kauer-Franz, 2024). I wouldn't treat that ending as permission to stop listening after release. New tasks or working conditions could change what users need.

What I find useful is the connection between understanding a problem and making the requirements testable. Instead of writing that an incident page should be easy to use, I'd specify a task. For example, an analyst should be able to identify the affected account, locate the evidence supporting the alert and explain the proposed response before confirming it. A usability session could then show where that sequence breaks down. The team would have something more useful than opinions about whether the page looks clean.

IDEO.org (2015) organizes its approach around Inspiration, Ideation and Implementation. Its Field Guide also emphasizes empathy, making ideas tangible, learning from failure, embracing ambiguity, optimism, creative confidence and iteration. I see this as a helpful way to approach the uncertainty that exists before the team understands the problem. Interviews and observation can challenge the first idea. A rough prototype can expose problems before the team invests heavily in implementation.

The two approaches share a reliance on people and feedback, but their emphasis differs. ISO gives me a structure for turning context into requirements and evaluating the result. IDEO encourages me to stay open long enough to discover a better solution. I'd use both. I'd want clear responsibilities and acceptance criteria, while allowing a prototype to prove that my original layout wasn't useful. Following a process shouldn't be an excuse to defend a design that users struggle with.

Perception Determines What Gets Attention

An investigation screen might contain an incident summary, affected entities, a timeline, evidence and possible actions. Simply putting all of that on one page doesn't establish which part deserves attention first. Gordon (2021) explains that visual hierarchy uses differences in contrast, scale and grouping to guide attention. Those choices communicate importance before someone has read every label.

I'd give the incident summary and current status a clear position, then group the supporting evidence by its relationship to the investigation. A change in heading size could separate sections, while spacing could show which details belong together. I'd use explicit labels alongside color so the meaning doesn't depend on noticing a particular shade. These are ways to make the page easier to interpret without removing information that an analyst may need.

Hierarchy also needs to represent the right priorities. In my proposed layout, a large response button shouldn't dominate the evidence needed to justify using it. A bright warning on every row could make it difficult to distinguish a significant finding from routine context. I'd test whether analysts notice the relevant evidence and interpret its meaning correctly. Finding the most visually prominent item is only useful if that item deserves the attention it receives.

Four UX Laws Applied to an Investigation

Jakob's law concerns the expectations people bring from other interfaces. Familiar patterns let people apply what they already know instead of learning every interaction again (Yablonski, n.d.-c). For Microsoft security tools, I'd favor consistent locations and labels for search, filters, incident details and navigation. If an analyst moves between related views, I'd want the same kind of action to behave predictably. I'd still consider a new pattern when it solves a real problem, but I'd test whether users understand it before assuming the change is an improvement.

Fitts's law connects the effort of selecting a target to its size and distance (Yablonski, n.d.-a). I'd apply it by making common investigation controls easy to select and placing them near the information they affect. I'd also separate controls that could be confused. Opening evidence and taking a disruptive response should have distinct labels and enough space between them. Making a control easy to reach doesn't mean every action should happen immediately. For a consequential response, I'd want a confirmation that identifies the affected account or device and explains the action.

Hick's law describes how decision time increases with the number and complexity of choices. Yablonski (n.d.-b) also warns against simplifying an interface until its meaning becomes unclear. I'd organize available actions around the task and reveal additional options when they're relevant. An analyst reviewing an alert shouldn't have to sort through every administrative feature. However, hiding everything behind unlabeled icons would create a different problem. I'd aim for a manageable set of clearly explained choices, with a visible path to advanced tools when the investigation requires them.

Miller's law points toward the value of organizing information into meaningful chunks. The practical lesson isn't that every menu must contain seven items; memory capacity varies with the person and context (Yablonski, n.d.-d). I'd group account details, device information and event history into recognizable sections. I'd also keep important investigation context visible when someone opens supporting evidence. An analyst shouldn't have to remember several identifiers while moving between views if the interface can carry that information forward. Useful grouping should reduce the work of understanding relationships, rather than divide the page into arbitrary boxes.

Empathy Includes the Conditions Around the Screen

For me, empathy means taking the analyst's circumstances seriously. I'd want to understand interruptions, handoffs and the pressure to decide whether an account is actually compromised. I wouldn't assume that knowing the product means someone can interpret every screen without difficulty. I'd ask what information the person needs at that point in the investigation and what could cause them to misunderstand the next step.

IDEO.org's (2015) emphasis on learning directly from people is relevant here. A designer can imagine a workflow, but observing someone attempt it can reveal a different problem. For example, my initial assumption might be that an investigation needs fewer screens. Testing could show that the real issue is losing the selected account and time range between those screens. Keeping that context might help more than combining everything into a crowded page.

I'd pay particular attention to the language around response actions. A confirmation should help the analyst understand scope and consequences, rather than ask an empty question about whether they're sure. If the proposed response affects a device, the interface should identify that device clearly. I'd want users to explain what they expect to happen before they confirm it. That would help distinguish a deliberate decision from a click based on an incorrect assumption.

Test Whether the Design Supports the Decision

I'd begin with a simple prototype and a realistic investigation scenario. The analyst would review the alert, inspect the evidence, explain their conclusion and select an appropriate next step. I'd observe where they hesitate, lose context, or misunderstand a label. I'd also ask them to explain their reasoning, because reaching the intended button doesn't prove they understood the information behind it.

Franz and Kauer-Franz (2024) describe evaluation as a way to check requirements, discover new ones and identify strengths and weaknesses. I'd use those findings to make focused changes and repeat the relevant tasks. If users consistently overlook an important event, I'd examine its placement and labeling. If they misunderstand an action, I'd revise the wording or interaction. I'd avoid redesigning unrelated parts of the interface just because a test exposed one problem.

I'd judge the result by whether the interface supports a clear, informed investigation. Speed matters, but I'd also consider whether analysts identify the right account, understand the evidence and recognize the scope of a response. The goal is a tool that helps people make sound decisions with the information available. In a security environment, human-centered design belongs in that work from the beginning, because the person interpreting the evidence is part of what makes the system effective.
